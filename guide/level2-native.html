UnCrackable Level 2 풀기

    Java 밖으로 숨은 코드를 읽는 법

    Level 2는 비밀번호 검사 코드를 Java가 아니라 C로 만들어서 숨겨두었습니다. 그래서 jadx로 열어도 핵심 코드가 보이지 않습니다. 이번에는 CPU가 직접 읽는 명령어(어셈블리)를 읽는 법을 기초부터 배웁니다.

    ① 비유로 감 잡기② 실제 데이터 보기③ 직접 해보기④ 확인 문제

    어셈블리가 처음이라면 0부(내 코드 뜯어보기)를 먼저 보면 훨씬 쉽습니다. 1부도 먼저 보고 오세요. 바이트, 16진수, Java 코드 읽기는 1부 내용을 그대로 씁니다. 6장에는 "먼저 생각해 보기"가 있습니다. 정답을 펼치기 전에 한 번씩 스스로 답해 보세요.

    0장

    Level 2는 무엇이 달라졌나

    겉모습은 Level 1과 같습니다. 그런데 jadx로 비밀번호 검사 코드를 따라가면 내용이 없는 메서드에서 길이 끊깁니다.

    1부에서 배운 방법으로 따라가 보기

    Level 1과 똑같이 verify()에서 시작하면 CodeCheck.a()에 도착합니다.

    public class CodeCheck {
    private native boolean bar(byte[] bArr);      // 내용({ })이 없음!

    public boolean a(String str) {
        return bar(str.getBytes());                // 입력값을 바이트로 바꿔서 bar에 넘김 (1부 1장)
    }
}

    bar()에는 { … }가 없고 앞에 native라는 단어가 붙어 있습니다. "이 메서드의 실제 내용은 Java가 아닌 다른 곳에 있다"는 뜻입니다. 그 다른 곳이 어디인지는 MainActivity 위쪽에 적혀 있습니다.

    static {
    System.loadLibrary("foo");    // libfoo.so 파일을 불러옴
}

    새로 생긴 것들

    코드뜻어디서 배우나
    native boolean bar(…)비밀번호 검사를 C 코드에 맡김1장, 6장
    System.loadLibrary("foo")C 코드가 든 libfoo.so를 불러옴1장
    native void init()앱이 켜질 때 C 코드로 무언가를 준비함7장
    Debug.isDebuggerConnected()0.1초마다 디버거가 붙었는지 확인함7장

    루팅 탐지와 디버그 가능 검사는 Level 1과 같습니다. 클래스 이름만 c → b, b → a로 바뀌었습니다.

    jadx에서 bar()의 내용이 보이지 않는 이유는?
    jadx는 classes.dex(Java 쪽 코드)만 디컴파일합니다. native 메서드의 내용은 APK 안의 lib/ 폴더에 있는 .so 파일에 있어서 다른 도구로 봐야 합니다.
    1장

    네이티브 코드: CPU가 바로 읽는 코드

    C로 만든 코드는 CPU가 바로 실행하는 기계어로 바뀝니다. Java와 C를 이어주는 규칙을 JNI라고 합니다.

    비유

    Java 앱을 한국 회사, C 코드를 외주 업체라고 생각해 보세요. 한국 회사는 "비밀번호 검사는 외주 업체에 맡긴다"고 적어둡니다(native). 외주 업체의 작업 내용은 회사 문서(classes.dex)가 아니라 외주 업체 쪽 문서(libfoo.so)에 있습니다. 그런데 이 문서는 한국어가 아니라 CPU의 언어(기계어)로 쓰여 있습니다. 둘 사이의 연락 규칙이 JNI입니다.

    왜 Java보다 읽기 어려운가

    Java (classes.dex)C (.so)
    컴파일 결과Java 전용 바이트코드CPU 기계어
    남아 있는 정보클래스 구조, 메서드 종류, 문자열이 대부분 남음변수 이름, 자료형, 구조가 대부분 사라짐
    되돌린 결과원본에 가까운 Java 코드어셈블리, 또는 거칠게 복원한 C 코드

    개발자가 C를 쓰는 이유는 보통 속도나 기존 C 라이브러리 때문입니다. 하지만 Level 2처럼 읽기 어렵게 만들려고 중요한 코드를 C로 옮기는 경우도 많습니다.

    lib 폴더에는 같은 코드가 4벌 있습니다

    CPU 종류마다 기계어가 다르기 때문에, APK 안에는 같은 C 코드를 CPU별로 컴파일한 파일이 따로 들어 있습니다.

    폴더CPU어디서 쓰나
    lib/arm64-v8a/ARM 64비트요즘 휴대폰 대부분
    lib/armeabi-v7a/ARM 32비트오래된 휴대폰
    lib/x86_64/Intel/AMD 64비트PC에서 돌리는 에뮬레이터
    lib/x86/Intel/AMD 32비트오래된 에뮬레이터

    이 교재는 x86_64 버전을 봅니다. 지금 쓰는 PC에 설치된 objdump가 이 종류를 읽을 수 있기 때문입니다. 네 파일은 같은 C 코드에서 나왔으므로 하는 일은 똑같습니다.

    Java 메서드와 C 함수를 짝짓는 이름 규칙

    Java가 bar()를 부르면 JNI는 .so 안에서 정해진 규칙으로 만든 이름의 함수를 찾아 실행합니다. 규칙은 Java_ + 패키지와 클래스(점을 밑줄로) + _ + 메서드 이름입니다.

    JNI 함수 이름 만들어 보기

    이 규칙 덕분에 .so 파일을 열었을 때 어느 함수가 Java의 어느 메서드인지 바로 알 수 있습니다. 5장에서 실제 파일로 확인합니다.

    MainActivity의 native void init()에 해당하는 C 함수 이름은? (위 입력칸으로 확인해 보세요)
    패키지와 클래스의 점(.)이 모두 밑줄(_)로 바뀌고 앞에 Java_가 붙습니다.
    2장

    CPU, 레지스터, 메모리, 스택

    CPU는 아주 적은 수의 빠른 저장칸(레지스터)에 값을 올려놓고 계산합니다. 많은 데이터는 메모리에 두고 필요할 때 가져옵니다.

    비유: 요리사의 주방

    CPU는 요리사입니다. 요리사는 한 번에 한 동작씩만 합니다.
    레지스터는 요리사의 손과 도마입니다. 아주 빠르지만 몇 개 없습니다.
    메모리는 냉장고입니다. 많이 담을 수 있지만 꺼내 오는 데 시간이 걸립니다. 칸마다 번호(주소)가 붙어 있습니다.
    스택은 냉장고 중에서 지금 만드는 요리용 임시 칸입니다. 요리(함수)가 끝나면 비웁니다.

    x86-64에서 자주 보는 레지스터

    레지스터는 이름이 정해져 있고, 쓰임새에도 약속이 있습니다. Level 2를 읽는 데는 아래 정도면 충분합니다.

    이름약속된 쓰임
    rdi, rsi, rdx, rcx함수를 부를 때 넘기는 값 1번째, 2번째, 3번째, 4번째
    rax함수가 끝날 때 돌려주는 값(결과)
    rsp스택(임시 칸)이 지금 어디서 시작하는지 가리키는 주소
    rbx, r14, r15함수 안에서 값을 잠시 보관할 때 씀

    예를 들어 C에서 strncmp(a, b, 23)을 부르면, 기계어에서는 rdi에 a, rsi에 b, rdx에 23을 넣고 함수로 점프합니다. 결과는 rax에 담겨 돌아옵니다.

    같은 레지스터의 일부만 쓰기

    rax는 8바이트짜리 칸입니다. 그중 일부만 쓸 때는 이름이 바뀝니다. 서랍 하나를 통째로 쓰거나 앞쪽 칸만 쓰는 것과 같습니다.

    이름크기뜻
    rax8바이트전체
    eax4바이트아래쪽 절반
    ax2바이트아래쪽 2바이트
    al1바이트맨 아래 1바이트

    edx는 rdx의 아래쪽, r14는 이름 규칙이 조금 다르지만 같은 원리입니다. 처음에는 "eax와 al은 rax의 일부"만 기억하면 됩니다.

    C 코드 strncmp(input, secret, 23)을 부를 때, 숫자 23은 어느 레지스터에 들어갈까요?
    세 번째 값이므로 rdx입니다. 6장에서 mov edx, 0x17이라는 줄을 보게 되는데, 0x17은 16진수로 23입니다.
    3장

    어셈블리 명령어 읽기

    어셈블리는 기계어를 사람이 읽을 수 있게 짧은 영어 단어로 적은 것입니다. 한 줄이 CPU의 한 동작입니다.

    비유

    어셈블리는 아주 꼼꼼한 요리 순서표입니다. "양파를 오른손에 든다", "오른손 양파를 도마에 놓는다", "무게가 200g인지 본다", "아니면 7번 줄로 가라"처럼 한 줄에 동작 하나만 적혀 있습니다. 줄 수가 많아서 길어 보이지만 한 줄 한 줄은 단순합니다.

    Level 2에 나오는 명령어

    명령어뜻C로 쓰면
    mov a, bb를 a에 복사함. 오른쪽에서 왼쪽으로 읽음a = b
    add a, b / sub a, b더하기 / 빼기a += b / a -= b
    cmp a, ba와 b를 비교하고 결과를 표시판(플래그)에 적어둠if (a == b)의 앞부분
    je 주소 / jne 주소표시판이 "같음"이면 / "다름"이면 그 주소로 점프if의 뒷부분
    test eax, eaxeax가 0인지 확인해서 표시판에 적음if (eax == 0)의 앞부분
    xor eax, eaxeax를 0으로 만듦 (자주 보는 관용구)eax = 0
    call 함수 / ret함수 부르기 / 함수 끝내고 돌아가기함수() / return
    push / pop스택에 값 쌓기 / 꺼내기 (보통 시작과 끝의 정리 작업)없음

    대괄호와 크기 표시

    [rsp+0x10]처럼 대괄호가 있으면 "그 주소에 있는 메모리 칸"이라는 뜻입니다. 대괄호가 없으면 레지스터나 숫자 자체입니다. 메모리에 쓸 때는 몇 바이트를 쓸지 앞에 적습니다.

    표시크기
    BYTE PTR1바이트
    WORD PTR2바이트
    DWORD PTR4바이트
    QWORD PTR8바이트

    예: mov BYTE PTR [rsp+0x16], 0x68 = "스택 시작에서 0x16(22)번째 칸에 1바이트짜리 값 0x68을 넣어라".

    직접 해보기: CPU가 되어 한 줄씩 실행하기

    아래는 "입력 길이가 23인지 검사하는" 짧은 어셈블리입니다. 6장의 실제 코드에 들어 있는 부분을 단순하게 줄였습니다. 입력 길이를 바꿔 가며 한 줄씩 실행해 보세요.

    한 줄씩 실행기

    ZF(Zero Flag)가 표시판입니다. cmp는 속으로 a − b를 계산하는데, 결과가 0이면(=같으면) ZF를 1로 켭니다. jne는 ZF가 0일 때(=다를 때) 점프합니다.

    mov edx, 0x17을 실행하면?
    mov는 오른쪽 값을 왼쪽에 넣습니다. 그리고 대괄호가 없으니 메모리가 아니라 레지스터 edx 자체에 넣습니다.
    4장

    리틀 엔디안: 숫자를 거꾸로 저장하는 방식

    여러 바이트짜리 숫자를 메모리에 넣을 때, x86과 ARM CPU는 작은 자리 바이트부터 앞 칸에 넣습니다. 그래서 메모리에서는 순서가 뒤집혀 보입니다.

    비유

    택배 상자 4개에 "1 2 3 4"라는 번호를 나눠 붙여서 트럭에 싣는다고 해보세요. 사람은 앞에서부터 1, 2, 3, 4 순서로 싣는 게 자연스럽습니다. 그런데 이 CPU들은 끝자리(4)부터 트럭 맨 앞에 싣습니다. 그래서 트럭 안을 앞에서부터 보면 4, 3, 2, 1입니다. 이 방식을 리틀 엔디안이라고 합니다(작은 쪽 끝이 먼저).

    실제 데이터: Level 2에 나오는 숫자

    Level 2 코드에는 mov DWORD PTR [rsp+0x10], 0x66206568이라는 줄이 있습니다. 4바이트 숫자 0x66206568을 메모리에 넣으라는 뜻입니다.

    바이트 순서글자로 읽으면
    코드에 적힌 순서66 20 65 68f ␣ e h
    메모리에 들어간 순서68 65 20 66h e ␣ f

    코드만 보면 "f eh"처럼 보이지만 실제 메모리에는 "he f"가 들어갑니다. 1부 1장에서 본 글자표로 확인할 수 있습니다(0x68 = h, 0x65 = e, 0x20 = 띄어쓰기, 0x66 = f).

    숫자를 메모리 순서로 바꿔보기

    왜 이게 중요한가

    개발자가 문자열을 숫자 명령어 속에 나눠 넣으면, 파일에서 글자를 검색해도 찾을 수 없습니다. 글자 순서가 뒤집혀 있고 명령어 사이사이에 흩어져 있기 때문입니다. 5장에서 실제로 글자 검색이 중간에 끊기는 것을 보게 됩니다.

    mov WORD PTR [rsp+0x14], 0x7369는 메모리에 어떤 두 글자를 넣을까요? (0x73 = s, 0x69 = i)
    코드에는 73 69(s i) 순서로 적혀 있지만, 메모리에는 뒤집혀서 69 73, 즉 "is"가 들어갑니다. 위 입력칸에 7369, WORD를 넣어 확인해 보세요.
    5장

    도구로 .so 파일 열어보기

    어셈블리를 무작정 처음부터 읽지 않습니다. 먼저 함수 목록과 글자를 훑어서 어디를 볼지 정합니다.

    이 장의 명령은 직접 터미널에서 실행할 수 있습니다. Claude Code 입력창에 !를 붙여서 붙여넣으면 결과가 대화에 남습니다. 모두 이 PC에 이미 설치된 도구입니다.

    1단계: APK에서 .so 꺼내기

    APK는 ZIP이므로 압축만 풀면 됩니다(1부 0장).

    ! cd ~/Desktop/reversing-lab && mkdir -p work/level2 && unzip -o -q apks/UnCrackable-Level2.apk 'lib/*' -d work/level2 && ls work/level2/lib

    1장에서 본 폴더 4개(arm64-v8a, armeabi-v7a, x86, x86_64)가 나옵니다.

    2단계: 이 파일이 가진 함수 목록 보기 (nm)

    ! nm -D --defined-only ~/Desktop/reversing-lab/work/level2/lib/x86_64/libfoo.so
    (실제 결과 중 일부)
0000000000001110 T Java_sg_vantagepoint_uncrackable2_CodeCheck_bar
0000000000001100 T Java_sg_vantagepoint_uncrackable2_MainActivity_init

    1장의 이름 규칙 그대로입니다. 앞의 숫자는 그 함수가 파일 안 어느 주소에서 시작하는지입니다. bar는 0x1110번지에 있습니다.

    3단계: 이 파일이 빌려 쓰는 함수 보기

    ! nm -D --undefined-only ~/Desktop/reversing-lab/work/level2/lib/x86_64/libfoo.so

    결과에 strncmp, fork, ptrace, waitpid 등이 나옵니다. 이 이름들이 중요한 단서입니다.

    함수하는 일짐작할 수 있는 것
    strncmp두 문자열을 정해진 길이만큼 비교함입력값과 정답을 비교하는 곳이 있음
    fork, ptrace, waitpid프로세스 복제, 다른 프로세스 감시디버거 방해 장치가 있음 (7장)

    4단계: 파일 안의 글자 찾기 (strings)

    ! strings ~/Desktop/reversing-lab/work/level2/lib/x86_64/libfoo.so | grep -i thanks
    Thanks for all t

    수상한 문장이 보이는데 "t"에서 끊겨 있습니다. 나머지 글자는 어디 갔을까요? 4장에서 배운 대로, 나머지는 명령어 속에 숫자로 들어가 있습니다. 그걸 확인하려면 어셈블리를 봐야 합니다.

    5단계: bar 함수의 어셈블리 보기 (objdump)

    ! objdump -d -M intel --no-show-raw-insn --disassemble=Java_sg_vantagepoint_uncrackable2_CodeCheck_bar ~/Desktop/reversing-lab/work/level2/lib/x86_64/libfoo.so
    • -d: 기계어를 어셈블리로 바꿔서 보여줌
    • -M intel: mov 목적지, 원본 순서로 보여줌 (3장에서 배운 순서)
    • --disassemble=함수이름: 그 함수만 보여줌

    결과는 6장에서 한 줄씩 읽습니다.

    실무에서는 Ghidra(미국 NSA가 공개한 무료 도구)를 많이 씁니다. 어셈블리를 C 비슷한 코드로 복원해 주고 화면으로 따라가기 편합니다. 설치 파일이 커서 이번에는 이미 설치된 objdump로 진행하고, Ghidra는 나중에 따로 다룹니다.

    strings로 "Thanks for all t"까지만 보이는 이유는?
    strings는 파일에서 글자가 연달아 있는 부분만 찾습니다. 나머지 7글자는 mov 명령어 속 숫자로 흩어져 있고, 리틀 엔디안으로 뒤집혀 있어서 글자처럼 보이지 않습니다.
    6장

    bar 함수를 한 덩어리씩 읽기

    bar 함수는 46줄입니다. 다섯 덩어리로 나눠서, 각 덩어리가 무엇을 하는지만 알아내면 됩니다.

    아래는 5단계 objdump 결과를 그대로 옮긴 것입니다. 오른쪽 설명은 이 교재에서 덧붙였습니다. 덩어리마다 먼저 생각해 보기에 스스로 답한 다음 정답을 펼쳐 보세요.

    덩어리 A: 시작 준비와 init 확인

    1110push r15시작할 때 하는 정리 작업 (무시해도 됨)
    1112push r14
    1114push rbx
    1115sub rsp,0x20스택에 임시 칸 32바이트 마련
    1119mov r14,rdx3번째 값(rdx)을 r14에 보관
    111cmov rbx,rdi1번째 값(rdi)을 rbx에 보관
    111fmov rax,QWORD PTR fs:0x28스택 보호 장치 (컴파일러가 자동으로 넣음, 무시)
    1128mov QWORD PTR [rsp+0x18],rax
    112dcmp BYTE PTR [rip+0x2ed8],0x1어떤 메모리 칸(0x400c)이 1인지 비교
    1134jne 119a1이 아니면 119a로 점프

    JNI 규칙상 C 함수는 Java에서 받은 값 앞에 두 개를 더 받습니다. 그래서 bar(byte[] bArr)의 C 함수는 이렇게 생겼습니다.

    bar(JNIEnv *env, jobject this, jbyteArray bArr)
     ↑ rdi           ↑ rsi          ↑ rdx

    먼저 생각해 보기: r14와 rbx에는 각각 무엇이 보관됐나요? 그리고 0x400c 칸은 누가 1로 만들까요? (힌트: 이 파일에서 함수가 하나 더 있었습니다)

    정답 펼치기

    r14 = 사용자 입력(bArr), rbx = JNIEnv(Java와 연락할 때 쓰는 연락처 수첩)입니다.

    0x400c 칸은 init() 함수가 1로 만듭니다. objdump로 init을 보면 mov BYTE PTR [rip+0x2eff],0x1 # 400c가 있습니다. 즉 init이 먼저 실행되지 않았으면 bar는 무조건 실패합니다. 실행 순서를 바꾸는 우회를 막는 장치입니다.

    덩어리 B: 스택에 글자 조립하기 (핵심)

    1136mov QWORD PTR [rsp+0x10],0x016~23번 칸을 0으로 비움
    113fmovaps xmm0,XMMWORD PTR [rip+0x7a]파일의 0x11c0번지에서 16바이트를 읽어옴
    1146movaps XMMWORD PTR [rsp],xmm0그 16바이트를 0~15번 칸에 씀
    114amov DWORD PTR [rsp+0x10],0x6620656816~19번 칸에 4바이트
    1152mov WORD PTR [rsp+0x14],0x736920~21번 칸에 2바이트
    1159mov BYTE PTR [rsp+0x16],0x6822번 칸에 1바이트

    xmm0은 16바이트를 한 번에 옮기는 큰 레지스터입니다. 0x11c0번지에는 strings로 본 "Thanks for all t"가 들어 있습니다. objdump로 확인할 수 있습니다.

    ! objdump -s -j .rodata ~/Desktop/reversing-lab/work/level2/lib/x86_64/libfoo.so

    먼저 생각해 보기: 4장의 리틀 엔디안을 적용하면 0~22번 칸에 어떤 문장이 완성될까요? 종이에 23칸을 그려서 채워 보세요.

    스택 조립 과정 따라가기

    버튼을 누를 때마다 명령어 한 줄을 실행하고, 새로 쓴 칸을 강조합니다.

    덩어리 C: 사용자 입력 꺼내기

    115emov rax,QWORD PTR [rbx]JNIEnv 수첩을 펼침
    1161xor edx,edx3번째 값 = 0
    1163mov rdi,rbx1번째 값 = env
    1166mov rsi,r142번째 값 = 사용자 입력 배열
    1169call QWORD PTR [rax+0x5c0]수첩의 0x5c0 위치 함수 = GetByteArrayElements
    116fmov r15,rax결과(입력 바이트들의 주소)를 r15에 보관
    1172mov rax,QWORD PTR [rbx]
    1175mov rdi,rbx
    1178mov rsi,r14
    117bcall QWORD PTR [rax+0x558]수첩의 0x558 위치 함수 = GetArrayLength

    JNIEnv는 Java 쪽에 일을 부탁하는 함수들의 목록(연락처 수첩)입니다. 목록에서 몇 번째 칸인지가 숫자로만 보여서 처음에는 무슨 함수인지 알 수 없습니다. 한 칸이 8바이트이므로 0x5c0 ÷ 8 = 184번째, 0x558 ÷ 8 = 171번째이고, JNI 공식 문서의 함수 목록에서 그 순번을 찾으면 이름이 나옵니다. Ghidra는 이 작업을 자동으로 해줍니다.

    정리하면 C에서는 Java의 byte[]를 바로 쓸 수 없어서, JNI에 부탁해 바이트들을 꺼내고(r15) 길이를 물어본(rax) 것입니다.

    덩어리 D: 길이 검사와 비교

    1181cmp eax,0x17입력 길이가 0x17(23)인지 비교
    1184jne 119a아니면 119a(실패)로
    1186mov rsi,rsp2번째 값 = 스택에 조립한 문장
    1189mov edx,0x173번째 값 = 23
    118emov rdi,r151번째 값 = 사용자 입력
    1191call 830 <strncmp@plt>strncmp(입력, 조립한 문장, 23)
    1196test eax,eax결과가 0인지 확인
    1198je 11b60이면 11b6(성공)으로

    먼저 생각해 보기: 3장에서 해본 길이 검사와 무엇이 같나요? 그리고 strncmp는 두 문자열이 같을 때 무엇을 돌려줄까요?

    정답 펼치기

    1181~1184는 3장 실행기와 똑같은 cmp + jne 구조입니다. 길이가 23이 아니면 비교도 하지 않고 실패합니다.

    strncmp는 두 문자열이 같으면 0을 돌려줍니다(다르면 0이 아닌 값). 그래서 test eax,eax로 0인지 보고, 0이면 je로 성공 쪽으로 점프합니다. "같으면 0"이라 처음에는 헷갈리기 쉬운 부분입니다.

    덩어리 E: 결과 돌려주기

    119axor eax,eax실패: 결과 = 0 (false)
    119cmov rcx,QWORD PTR fs:0x28스택 보호 확인 (무시)
    11a5cmp rcx,QWORD PTR [rsp+0x18]
    11aajne 11ba
    11acadd rsp,0x20정리 작업
    11b0pop rbx
    11b1pop r14
    11b3pop r15
    11b5reteax 값을 Java에 돌려줌
    11b6mov al,0x1성공: 결과 = 1 (true)
    11b8jmp 119c정리 작업으로 이동

    성공이든 실패든 결과(eax)만 다르게 넣고 같은 정리 작업을 거쳐 Java로 돌아갑니다. Java의 verify()는 이 값으로 "Success!"나 "Nope..."를 띄웁니다.

    전체를 C로 복원하면

    다섯 덩어리를 C 코드로 다시 쓰면 이렇습니다. Ghidra가 보여주는 결과도 이와 비슷합니다.

    jboolean bar(JNIEnv *env, jobject this, jbyteArray input) {
    if (initialized != 1) return false;                 // 덩어리 A

    char secret[24] = {0};                              // 덩어리 B
    memcpy(secret, "Thanks for all t", 16);
    *(int   *)(secret + 16) = 0x66206568;
    *(short *)(secret + 20) = 0x7369;
    secret[22] = 0x68;

    char *in = (*env)->GetByteArrayElements(env, input, 0);   // 덩어리 C
    if ((*env)->GetArrayLength(env, input) != 23) return false; // 덩어리 D
    return strncmp(in, secret, 23) == 0;                // 덩어리 D, E
}

    정답 확인

    위 조립 실습의 결과나 직접 채운 23칸을 보고 정답을 적어 보세요. 1부처럼 Python으로 확인할 수도 있습니다.

    ! python3 -c "print(b'Thanks for all t' + (0x66206568).to_bytes(4,'little') + (0x7369).to_bytes(2,'little') + bytes([0x68]))"

    to_bytes(4, 'little')가 4장의 리틀 엔디안 변환입니다.

    Level 2에 새로 생긴 방어 장치

    Level 2는 디버거(실행 중인 앱을 멈추고 들여다보는 도구)를 막는 장치를 두 겹으로 넣었습니다. 지금처럼 파일만 읽는 정적 분석에는 영향이 없고, Level 3에서 앱을 실행하며 분석할 때 문제가 됩니다.

    1. C 쪽: 디버거 자리 미리 차지하기 (init)

    디버거는 앱에 달라붙어서 들여다봅니다. 그런데 리눅스에서는 한 프로그램에 디버거가 하나만 붙을 수 있습니다. Level 2는 이 점을 이용해 자기 자신의 복제본을 만들어 자기에게 먼저 붙여둡니다. 화장실 칸에 미리 들어가서 문을 잠가두는 것과 같습니다. 진짜 디버거가 오면 이미 자리가 차 있어서 붙을 수 없습니다.

    5장에서 본 fork(복제본 만들기)와 ptrace(다른 프로세스에 붙기)가 이 장치입니다. init 함수의 어셈블리에서 이 흐름이 보입니다.

    8e5call 7e0 <fork@plt>자기 복제본(자식)을 만듦
    90ecall 800 <getppid@plt>자식: 부모(원래 앱)의 번호를 알아냄
    915mov edi,0x101번째 값 = 0x10 = PTRACE_ATTACH (붙기)
    922call 810 <ptrace@plt>자식이 부모에게 디버거처럼 붙음
    9b8call 7d0 <_exit@plt>이상이 생기면 종료

    그리고 init은 마지막에 6장 덩어리 A에서 본 0x400c 칸을 1로 만듭니다. 이 장치를 건너뛰려고 init을 실행하지 않으면 bar가 항상 실패하게 묶어둔 것입니다.

    2. Java 쪽: 0.1초마다 디버거 확인

    SystemClock.sleep(100L);                // 0.1초 쉬고 다시 확인
}

MainActivity.this.a("Debugger detected!");  // 경고 후 종료
