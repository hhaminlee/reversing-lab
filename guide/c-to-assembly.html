    1장

    변수: 스택의 칸에 붙인 이름

    함수 안의 변수는 스택(임시 칸)의 어느 한 칸입니다. 어셈블리에는 변수 이름이 없고 "기준점에서 몇 칸 아래"라는 위치만 남습니다.

    비유

    함수가 시작되면 책상 서랍 하나를 받습니다. 서랍 맨 위를 기준점(rbp)으로 정하고, 변수 a는 "기준점에서 8칸 아래", b는 "4칸 아래"에 넣습니다. 컴파일하면 이름표(a, b)는 버려지고 위치만 남습니다. 그래서 어셈블리에는 [rbp-0x8]처럼 위치만 보입니다.

    내 코드와 어셈블리 짝짓기

    C 코드 줄이나 어셈블리 줄을 누르면 짝이 되는 줄이 함께 강조됩니다.

    읽는 요령

    • push rbp / mov rbp,rsp: 모든 함수의 시작 인사. "서랍 받고 기준점 정하기". 앞으로는 건너뛰고 읽어도 됨
    • [rbp-0x8]: 기준점에서 8바이트 아래 칸 = 변수 a
    • DWORD PTR: 4바이트짜리 칸. C의 int가 4바이트라서 DWORD로 나옴
    • a + 3은 메모리에서 바로 못 하고 레지스터(eax)로 가져와서 더한 뒤 다시 칸에 넣음. 2부 2장의 "요리사는 손(레지스터)에 들고 작업한다"는 비유 그대로임
    • 마지막에 돌려줄 값을 eax에 넣고 ret. 결과는 항상 eax로 돌려줌
    직접 바꿔보기 · 01_vars.c에서 int a = 5;를 int a = 100;으로 바꾸고 다시 실행해 보세요. mov DWORD PTR [rbp-0x8], 뒤의 숫자가 무엇으로 바뀔지 먼저 예상해 보세요. (힌트: 1부 2장의 16진수)
    ! ~/Desktop/reversing-lab/part0/show.sh 01_vars.c vars
    정답 펼치기

    0x64로 바뀝니다. 6×16 + 4 = 100입니다.

    어셈블리에서 변수 이름 a, b가 보이지 않는 이유는?
    이름은 사람을 위한 것입니다. 그래서 리버싱할 때는 [rbp-0x8] 같은 위치를 보고 우리가 이름을 다시 붙여줍니다. 1부 5장에서 jadx로 이름을 바꾸던 것과 같은 작업입니다.
    2장

    함수 호출: 값은 레지스터로 넘기고, 결과는 eax로 받는다

    함수를 부를 때 넘기는 값은 정해진 순서의 레지스터(edi, esi, edx…)에 담기고, 결과는 eax에 담겨 돌아옵니다.

    비유

    함수 호출은 배달 주문과 같습니다. 주문서의 1번 칸(edi)에 첫 번째 재료, 2번 칸(esi)에 두 번째 재료를 적어서 보냅니다(call). 요리가 끝나면 결과는 항상 정해진 그릇(eax)에 담겨 돌아옵니다. 칸 순서가 약속돼 있어서 주문하는 쪽과 요리하는 쪽이 서로 헷갈리지 않습니다.

    부르는 쪽: call_add

    줄을 눌러 짝을 확인해 보세요.

    불리는 쪽: add

    x는 edi로, y는 esi로 들어와서 각각 스택 칸에 보관됩니다.

    읽는 요령

    • call 바로 앞의 mov edi, …, mov esi, …를 보면 무엇을 넘기는지 알 수 있음
    • 함수 시작 부분에서 edi, esi를 어디에 저장하는지 보면 어느 칸이 어느 인자인지 알 수 있음
    • call 바로 뒤에서 eax를 쓰면 그게 함수의 결과임
    • 넘기는 순서가 C와 반대(esi 먼저, edi 나중)인 건 컴파일러 마음임. 순서보다 어느 레지스터에 넣었는지가 중요함

    2부 6장의 strncmp(입력, 정답, 23) 호출에서 rdi, rsi, edx에 값을 넣던 것이 바로 이 규칙입니다. edi는 rdi의 아래쪽 4바이트입니다(int는 4바이트, 주소는 8바이트).

    직접 바꿔보기 · 02_func.c의 add(3, 4)를 add(10, 20)으로 바꾸면 call_add의 어느 두 줄이 바뀔까요?
    ! ~/Desktop/reversing-lab/part0/show.sh 02_func.c call_add
    정답 펼치기

    mov esi,0x4 → mov esi,0x14(20), mov edi,0x3 → mov edi,0xa(10)로 바뀝니다.

    어셈블리에서 call 직전에 mov edx,0x17이 보였다면?
    인자 순서는 edi(1번째), esi(2번째), edx(3번째)입니다. 결과는 call 뒤의 eax로 돌아옵니다.
    3장

    if 문: 비교하고, 조건이 안 맞으면 건너뛴다

    if 문은 cmp와 점프 명령이 됩니다. 이때 조건이 거꾸로 뒤집힌다는 점이 가장 헷갈리는 부분입니다.

    비유

    C는 "23이면 이 안으로 들어가라"라고 씁니다. 어셈블리는 위에서 아래로만 흘러가기 때문에 거꾸로 씁니다. "23이 아니면 이 부분을 건너뛰어라". 그러면 23일 때는 건너뛰지 않으니 자연스럽게 안으로 들어가게 됩니다. 길 안내로 치면 "목적지면 내려라" 대신 "목적지가 아니면 다음 정거장으로 가라"라고 말하는 셈입니다.

    내 코드와 어셈블리 짝짓기

    C의 ==(같으면)가 어셈블리에서는 jne(다르면 점프)가 된 것을 확인하세요.

    조건 점프 명령 모음

    명령뜻 (cmp a, b 다음에)C 조건의 반대로 자주 나옴
    je / jne같으면 / 다르면 점프!= / ==
    jg / jlea가 크면 / 작거나 같으면 점프<= / >
    jl / jgea가 작으면 / 크거나 같으면 점프>= / <
    jmp조건 없이 무조건 점프else를 건너뛸 때

    2부 3장의 한 줄씩 실행기가 바로 이 구조였습니다. 거기서 실행해 본 감각을 떠올려 보세요.

    직접 바꿔보기 · 03_if.c의 n == 23을 n < 23으로 바꾸면 cmp와 점프가 어떻게 바뀔까요? 예상한 다음 확인해 보세요.
    ! ~/Desktop/reversing-lab/part0/show.sh 03_if.c check
    정답 펼치기

    cmp DWORD PTR [rbp-0x4],0x16 / jg …가 나옵니다. 숫자가 23이 아니라 22(0x16)로 바뀌었습니다.

    "n < 23"은 "n ≤ 22"와 같고, 그 반대인 "n > 22이면 건너뛰어라"로 바꾼 것입니다. 컴파일러는 이렇게 조건을 같은 뜻의 다른 모양으로 바꾸기도 합니다. 그래서 숫자 하나 차이로 헷갈리지 않게 점프 조건과 숫자를 같이 봐야 합니다.

    cmp eax,0x17 다음에 jne 실패가 있다면 원래 C 코드는?
    다르면(jne) 실패로 건너뛰므로, 같을 때만 그 아래(성공 쪽)를 실행합니다. 조건을 뒤집어 읽으면 원래 C 코드가 나옵니다.
    4장

    반복문: 위쪽 주소로 되돌아가는 점프

    어셈블리에서 반복문은 점프가 위쪽(더 작은 주소)을 가리키는 모양으로 알아볼 수 있습니다.

    비유

    요리 순서표에 "3번 줄로 돌아가라"는 지시가 있으면 반복입니다. 앞으로만 가던 흐름이 뒤로 돌아가는 화살표가 생깁니다. Ghidra 같은 도구는 이 화살표를 실제로 그려줍니다. 어셈블리에서 위쪽 주소로 가는 점프를 보면 "아, 반복문이구나" 하고 알아채면 됩니다.

    내 코드와 어셈블리 짝짓기

    for 줄을 누르면 어셈블리 세 군데(시작값, i++, 조건 검사)가 함께 강조됩니다. for 한 줄이 세 조각으로 나뉘어 있습니다.

    흐름 그려보기

    113e  jmp 114a ──────────────┐   ① 처음엔 조건 검사로 바로 감
1140  total += i   ◀──────┐   │
1146  i++                 │   │
114a  i <= n 인가? ◀──────┼───┘
1150  jle 1140 ───────────┘       ② 맞으면 위(1140)로 돌아감 = 반복
1152  return total               ③ 아니면 아래로 빠져나감

    jle 1140은 현재 위치(1150)보다 작은 주소로 갑니다. 이게 반복문의 표시입니다.

    어셈블리에서 11a0: jne 1180이 보였다면 무엇을 의심해야 할까요?
    점프 목적지(1180)가 현재 위치(11a0)보다 위쪽입니다. 위로 가는 점프는 거의 항상 반복문입니다. if 문은 보통 아래쪽으로 건너뜁니다.
    5장

    문자열: 컴파일러가 글자를 숫자로 쪼갠다

    함수 안에서 문자 배열을 만들면, 컴파일러는 글자들을 8바이트 숫자로 묶어서 명령어 안에 직접 넣습니다. 2부 Level 2에서 본 모습이 내 코드에서도 똑같이 나옵니다.

    비유

    이사할 때 책을 한 권씩 나르지 않고 8권씩 상자에 담아서 옮기는 것과 같습니다. 컴파일러는 "Thanks for all the fish" 23글자를 한 글자씩 넣는 대신 8글자씩 묶어서 숫자 하나로 만들고 한 번에 옮깁니다. 그 숫자는 2부 4장의 리틀 엔디안 규칙에 따라 거꾸로 적혀 있습니다.

    내 코드와 어셈블리 짝짓기

    C의 두 번째 줄(secret 만들기)을 누르면 movabs 세 줄이 강조됩니다. movabs는 8바이트 숫자를 레지스터에 넣는 명령입니다.

    숫자를 글자로 되돌려 보기

    movabs 숫자를 메모리 순서로 읽기

    세 번째 숫자는 7바이트만 적혀 있습니다. 맨 앞(가장 큰 자리)의 00이 생략된 것인데, 메모리에서는 맨 뒤로 가서 문장 끝 표시(0)가 됩니다.

    그 밖의 패턴

    • lea rdx,[rbp-0x20]: secret이 있는 위치(주소)를 계산함. 6장에서 자세히 봄
    • call strcmp → test eax,eax → sete al: C의 strcmp(…) == 0. sete는 "같으면(0이면) al을 1로" 만드는 명령임
    • fs:0x28, __stack_chk_fail: 2부에서 본 스택 보호 장치. 배열을 쓰는 함수에 컴파일러가 자동으로 넣음. 무시해도 됨
    2부 Level 2에서 정답 글자가 숫자로 쪼개져 있던 이유로 가장 그럴듯한 것은?
    내가 평범하게 쓴 코드도 똑같이 쪼개졌습니다. 숨기려는 의도가 있었는지와 상관없이, 컴파일러가 만든 모양이라는 걸 알면 당황하지 않고 읽을 수 있습니다. 7장에서 Level 2와 나란히 놓고 비교합니다.
    6장

    포인터: 주소를 담는 변수

    포인터는 값이 아니라 "어디에 있는지(주소)"를 담습니다. 어셈블리에서는 lea가 주소를 만들고, 대괄호 []가 그 주소로 찾아갑니다.

    비유

    친구에게 선물을 직접 주는 대신 "우리 집 주소"가 적힌 쪽지를 줬다고 해보세요. 친구는 그 쪽지를 보고 우리 집에 찾아가서 선물(7)을 놓고 갑니다. 쪽지 = 포인터, 쪽지 만들기 = &v = lea, 쪽지 보고 찾아가기 = *p = [rax]입니다.

    부르는 쪽: use_pointer

    &v가 lea rax,[rbp-0xc]로 바뀐 것을 확인하세요.

    불리는 쪽: set_seven

    *p = 7이 "주소를 rax로 꺼내고 → 그 주소의 칸에 7을 쓴다" 두 줄이 됩니다.

    lea와 mov의 차이 (가장 많이 헷갈리는 부분)

    명령하는 일비유
    lea rax,[rbp-0xc]주소를 계산해서 rax에 넣음. 칸 안의 값은 안 봄집 주소를 쪽지에 적기
    mov eax,DWORD PTR [rbp-0xc]그 주소의 칸에 들어 있는 값을 가져옴그 집에 들어가서 물건 가져오기

    set_seven에서 p를 저장할 때는 QWORD PTR(8바이트)입니다. 64비트 컴퓨터에서 주소는 8바이트라서, int(4바이트, DWORD)와 크기가 다릅니다. 크기 표시만 봐도 "이건 주소일지도"라고 짐작할 수 있습니다.

    lea rsi,[rsp+0x9] 다음에 call strcmp가 있다면 strcmp의 두 번째 인자는?
    lea는 주소만 만듭니다. strcmp는 두 문자열의 주소를 받아서 비교하기 때문에 lea로 주소를 넘기는 것입니다. 8장 crackme에 이 줄이 그대로 나옵니다.
    7장

    최적화(-O2): 실제 앱의 어셈블리는 이렇게 생겼다

    배포되는 앱은 빠르고 작게 만들려고 최적화해서 컴파일합니다. 결과는 짧아지지만 C 코드와 한 줄씩 짝지어지지 않습니다.

    비유

    -O0은 신입 요리사입니다. 레시피를 한 줄씩 그대로 따라 해서 느리지만 따라가기 쉽습니다. -O2는 숙련된 요리사입니다. 결과는 같은데 순서를 바꾸고, 여러 단계를 한 번에 하고, 필요 없는 단계는 빼버립니다. 빠르지만 옆에서 보면 레시피의 어느 줄을 하는 중인지 알기 어렵습니다.

    같은 if 문, 다른 결과

    -O0 (10줄)-O2 (4줄)
    push   rbp
mov    rbp,rsp
mov    DWORD PTR [rbp-0x4],edi
cmp    DWORD PTR [rbp-0x4],0x17
jne    113d
mov    eax,0x1
jmp    1142
mov    eax,0x0
pop    rbp
ret
    xor    eax,eax
cmp    edi,0x17
sete   al
ret
    • 변수를 스택 칸에 저장하지 않고 레지스터(edi)에서 바로 비교함
    • 점프 없이 sete(같으면 1)로 결과를 바로 만듦
    • 함수 시작 인사(push rbp)도 생략함

    반복문은 더 심하게 바뀝니다. 아래 명령으로 4장의 sum을 -O2로 보면 두 개씩 묶어서 더하는 등 원래 모양을 알아보기 어렵습니다. 지금은 이해하지 않아도 됩니다. "최적화하면 이렇게 낯설어질 수 있다"만 눈으로 확인하세요.

    ! ~/Desktop/reversing-lab/part0/show.sh 04_loop.c sum -O2

    핵심 장면: 내 코드 -O2 vs Level 2

    5장의 문자열 비교 코드를 -O2로 컴파일해서 2부 Level 2의 bar 함수와 나란히 놓아 보겠습니다.

    ! ~/Desktop/reversing-lab/part0/show.sh 05_string.c check_pw -O2
    하는 일내 코드 (05_string.c, -O2)Level 2 (libfoo.so)
    앞 16글자를 데이터 영역에서 읽기movdqa xmm0,XMMWORD PTR [rip+0xea4]movaps xmm0,XMMWORD PTR [rip+0x7a]
    스택에 16글자 쓰기movaps XMMWORD PTR [rsp],xmm0movaps XMMWORD PTR [rsp],xmm0
    나머지 글자를 숫자로 쓰기movabs rax,0x68736966206568
    (8바이트 한 번)    		0x66206568, 0x7369, 0x68
    (4 + 2 + 1바이트)
    문자열 비교call strcmpcall strncmp
    strings 검색 결과Thanks for all tThanks for all t

    거의 같습니다. 나머지 7글자를 쪼개는 크기만 다른데, 이건 컴파일러 종류와 버전(Level 2는 Android용 clang 7)이 달라서입니다. 즉 Level 2의 어셈블리는 아마 이런 평범한 C 코드에서 나왔을 겁니다.

    char secret[] = "Thanks for all the fish";
if (길이 == 23 && strncmp(입력, secret, 23) == 0) return 1;

    이제 2부 6장을 다시 보면 "어려운 숨기기 기술"이 아니라 컴파일러가 만든 익숙한 모양으로 보일 겁니다. 리버싱이 쉬워지는 순간이 바로 이렇게 "아, 이거 그 패턴이구나" 할 때입니다.

    실제 앱 분석에서 -O0처럼 깔끔한 어셈블리를 보기 어려운 이유는?
    최적화는 속도와 크기 때문에 켜는 것이지 숨기려는 목적이 아닙니다. 그래도 결과적으로 읽기가 어려워집니다. 그래서 리버싱하는 사람은 -O0과 -O2 패턴을 둘 다 알아두면 좋습니다.
    8장

    나만의 crackme를 만들고 직접 풀기

    비밀번호 검사 프로그램을 직접 만들고, 원본을 안 본 척하고 어셈블리만으로 풀어봅니다. 마지막에는 실행 중에 멈춰서 정답을 꺼내는 동적 분석도 맛봅니다.

    1단계: 프로그램 실행해 보기

    08_crackme.c는 이미 컴파일돼 있습니다. 아무 비밀번호나 넣어보세요.

    ! ~/Desktop/reversing-lab/part0/build/08_crackme-O2 hello

    Nope...이 나옵니다. 이제 C 파일을 열지 말고 정답을 찾아봅시다.

    build 폴더에 파일이 없다는 오류가 나오면 아래 2단계 명령을 먼저 실행하세요. show.sh가 컴파일까지 해줍니다.

    2단계: 어셈블리 보기 (정적 분석)

    ! ~/Desktop/reversing-lab/part0/show.sh 08_crackme.c check_pw -O2

    먼저 생각해 보기: 아래 질문에 어셈블리만 보고 답해 보세요.

    1. strlen 다음의 cmp rdx,0xe는 무엇을 검사하나요? 정답은 몇 글자인가요?
    2. movabs 두 줄의 숫자를 아래 도구로 글자로 바꾸면 무엇이 나오나요?
    3. 두 숫자를 쓰는 위치가 [rsp+0x9]와 [rsp+0x10]입니다. 0x9부터 8바이트를 쓰면 0x10까지 덮습니다. 겹치는 칸은 어떻게 될까요?
    movabs 숫자를 글자로
    정답 펼치기
    1. 입력 길이가 0xe(14)인지 검사합니다. 정답은 14글자입니다.
    2. 첫 번째 = robot-fm, 두 번째 = ms-2026 + 끝 표시(0)
    3. 0x10번 칸은 첫 번째 숫자의 마지막 글자 m과 두 번째 숫자의 첫 글자 m이 겹칩니다. 같은 글자라서 컴파일러가 겹쳐 쓴 것입니다. 이어 붙이면 robot-fms-2026입니다.
    ! ~/Desktop/reversing-lab/part0/build/08_crackme-O2 robot-fms-2026

    3단계: strings로는 왜 안 보일까

    ! strings ~/Desktop/reversing-lab/part0/build/08_crackme-O2 | grep robot

    robot-fmH처럼 조각만 나옵니다. 글자가 명령어 안의 숫자로 들어가 있어서, 뒤에 이어지는 다음 명령어 바이트(H)까지 글자로 착각한 것입니다. strings는 빠른 단서 찾기 도구일 뿐이고, 정확한 답은 어셈블리를 읽어야 나옵니다.

    4단계: 실행 중에 멈춰서 꺼내기 (동적 분석 맛보기)

    지금까지는 레시피만 읽었습니다(정적 분석). 이번에는 요리사가 요리하는 중에 "잠깐 멈춰!" 하고 손에 뭘 들고 있는지 보는 겁니다. 이 도구가 디버거(gdb)입니다. strcmp가 불리는 순간 멈추면, 2장에서 배운 대로 rdi에 내 입력, rsi에 정답의 주소가 들어 있습니다.
    ! gdb -q -batch -ex 'break main' -ex 'run' -ex 'break strcmp' -ex 'continue' -ex 'x/s $rdi' -ex 'x/s $rsi' --args ~/Desktop/reversing-lab/part0/build/08_crackme-O2 aaaaaaaaaaaaaa
    • break main → run: 프로그램 시작 직후에 멈춤
    • break strcmp → continue: strcmp가 불리는 순간 다시 멈춤
    • x/s $rdi, x/s $rsi: 두 레지스터가 가리키는 주소의 문자열을 보여줌

    마지막 두 줄에 'a' <repeats 14 times>(내 입력)와 "robot-fms-2026"(정답)이 나옵니다.

    먼저 생각해 보기: 입력을 aaaaaaaaaaaaaa(14글자)로 넣은 이유가 있습니다. hello로 넣으면 strcmp에서 멈추지 않습니다. 왜일까요?

    정답 펼치기

    길이 검사(cmp rdx,0xe / jne)에서 14글자가 아니면 strcmp를 부르지 않고 바로 실패로 건너뛰기 때문입니다. 동적 분석을 할 때도 원하는 지점까지 실행이 도달하도록 입력을 맞춰야 합니다. 정적 분석으로 먼저 구조를 알아두면 이런 걸 미리 알 수 있습니다.

    2부 7장의 디버거 방어 장치가 막으려던 게 바로 이 작업입니다. Level 3에서는 gdb 대신 Frida로 같은 일을 Android 앱에 합니다.

    5단계: 문제를 바꿔서 다시 풀기

    08_crackme.c의 "robot-fms-2026"을 다른 문장으로 바꾸고 다시 2~4단계를 해보세요. 글자 수를 8, 16, 20처럼 바꾸면 컴파일러가 쪼개는 방식도 달라집니다. 동료에게 실행 파일만 주고 풀어보게 해도 좋습니다.
