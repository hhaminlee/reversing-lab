    리버싱은 무엇을 거꾸로 하나

    사람이 쓴 코드는 기계용으로 바뀌어 배포됩니다. 리버싱은 그걸 다시 사람이 읽을 수 있게 되돌리는 일입니다.

    비유

    요리 레시피(소스코드)로 만든 완성된 요리(앱)만 받았다고 생각해 보세요. 리버싱은 요리를 맛보고 뜯어보면서 레시피를 다시 적어내는 일입니다. 완벽하게 똑같지는 않지만 무슨 재료를 어떤 순서로 썼는지는 알아낼 수 있습니다.

    앱이 만들어지는 과정

    Java 소스코드사람이 읽는 글
    → 컴파일 →
    classes.dex기계가 읽는 바이트코드
    → 묶기 →
    APK 파일설치 파일

    리버싱이 하는 일

    APK 파일
    → 압축 풀기 →
    classes.dex
    → jadx로 디컴파일 →
    Java 비슷한 코드변수 이름 등은 일부 사라짐

    APK 안에는 무엇이 있나

    APK는 사실 ZIP 압축 파일입니다. 확장자만 다릅니다. 안을 열면 이런 파일들이 있습니다.

    1장

    바이트: 컴퓨터는 모든 것을 숫자로 저장한다

    글자, 사진, 암호 키 모두 컴퓨터 안에서는 0부터 255 사이의 숫자들이 줄지어 있는 것입니다. 그 숫자 하나를 바이트라고 합니다.

    비유

    바이트는 숫자 하나가 들어가는 작은 칸입니다. 칸 하나에는 0~255 중 하나만 넣을 수 있습니다. 글자를 저장할 때는 약속된 표(ASCII, UTF-8)에 따라 글자를 숫자로 바꿔서 칸에 넣습니다. 예를 들어 A는 65, a는 97, 띄어쓰기는 32입니다.

    직접 해보기

    글자를 바이트로 바꿔보기
    큰 글자: 16진수 (2장에서 배움)작은 숫자: 10진수아래: 원래 글자

    영어는 글자 하나가 1바이트입니다. 한글은 글자 하나가 3바이트를 차지합니다. 그래서 "글자 수"와 "바이트 수"는 다를 수 있습니다.

    왜 중요한가

    암호화는 글자가 아니라 바이트를 다룹니다. 그래서 비밀번호를 풀려면 항상 "글자 → 바이트 → 암호 처리 → 바이트 → 글자" 순서를 거칩니다. Level 1 스크립트에서 계속 "바이트로 바꾼다"고 한 이유가 이것입니다.

    I want to believe는 몇 바이트일까요? (띄어쓰기도 글자입니다)
    I(1) + 띄어쓰기(1) + want(4) + 띄어쓰기(1) + to(2) + 띄어쓰기(1) + believe(7) = 17바이트. 위 입력칸에 넣어서 확인해 보세요. 이 숫자가 4장 패딩에서 다시 나옵니다.
    2장

    16진수: 바이트를 두 글자로 적는 방법

    바이트 하나(0~255)를 정확히 두 글자로 적는 표기법입니다. 0~9와 a~f, 16개 기호를 씁니다.

    비유

    우리는 10개 기호(0~9)로 숫자를 적습니다. 16진수는 16개 기호(0~9, a, b, c, d, e, f)를 씁니다. a=10, b=11 … f=15입니다. 이렇게 하면 0~255를 항상 딱 두 글자로 적을 수 있어서 바이트를 적기에 편합니다.
    10진수16진수계산
    65414×16 + 1 = 65
    1418d8×16 + 13(d) = 141
    255ff15×16 + 15 = 255 (가장 큰 바이트)

    코드에서는 16진수라는 표시로 앞에 0x를 붙입니다. 0x41은 65이고, 0x7f030000도 16진수로 적은 숫자입니다.

    실제 데이터: Level 1의 열쇠

    Level 1에 있던 8d127684cbc37c17616d806cf50473cc는 32글자입니다. 두 글자씩 끊으면 바이트 하나이므로 16바이트입니다.

    16진수 문자열을 바이트로 끊어보기

    아래 글자가 ·로 나오는 칸은 화면에 찍을 수 있는 글자가 아니라는 뜻입니다. 암호 키는 원래 글자가 아니라 무작위 숫자라서 대부분 이렇게 나옵니다.

    Level 1 코드에서는

    앱의 b() 메서드가 바로 이 일을 합니다. 두 글자씩 읽어서 바이트 하나로 만듭니다.

    // 문자열을 두 글자씩(i += 2) 읽음
for (int i = 0; i < length; i += 2) {
    bArr[i / 2] = (byte) ((Character.digit(str.charAt(i), 16) << 4)
                        + Character.digit(str.charAt(i + 1), 16));
}
    • Character.digit(글자, 16): 16진수 글자 하나를 숫자로 바꿈. '8' → 8, 'd' → 13
    • << 4: 16을 곱한 것과 같음. 앞 글자는 16의 자리이기 때문임
    • 결국 8×16 + 13 = 141. 위 표와 똑같은 계산임

    Python의 bytes.fromhex()는 이 반복문 전체를 한 줄로 해주는 함수입니다.

    16진수 4a는 10진수로 얼마일까요?
    4×16 + 10(a) = 74. 1장 입력칸에 대문자 J를 넣으면 4a, 74가 나옵니다.
    3장

    Base64: 잠금이 아니라 옮겨 적기

    화면에 찍을 수 없는 바이트를 안전한 글자 64종류로 바꿔 적는 방법입니다. 누구나 되돌릴 수 있으므로 비밀 보호 효과는 없습니다.

    비유

    외국어 이름을 한글로 소리 나는 대로 적는 것과 비슷합니다. "Seoul"을 "서울"로 적어도 뜻이 숨겨지지 않습니다. 규칙만 알면 누구나 원래대로 돌려놓을 수 있습니다. 이렇게 규칙에 따라 표기만 바꾸는 것을 인코딩이라고 하고, 열쇠가 있어야만 풀리는 암호화와는 다릅니다.
    인코딩 (hex, Base64)암호화 (AES)
    목적바이트를 글자로 옮겨 적기내용을 숨기기
    열쇠없음필요함
    되돌리기누구나 가능열쇠가 있어야 가능

    왜 옮겨 적어야 하나

    암호화된 결과는 1장에서 본 ·처럼 화면에 찍을 수 없는 바이트투성이입니다. Java 소스코드는 글자로 써야 하니 이런 바이트를 그대로 넣을 수 없습니다. 그래서 개발자는 Base64로 바꿔서 코드에 적어둡니다.

    Base64는 영문 대소문자, 숫자, +, / 64종류를 씁니다. 길이를 맞추려고 끝에 =가 붙는 경우가 많아서, =로 끝나는 문자열을 보면 Base64를 의심하면 됩니다.

    Base64 ↔ 바이트 바꿔보기

    Level 1의 상자를 되돌려 보면 32바이트가 나오고, 대부분 ·입니다. Base64는 벗겨냈지만 아직 AES로 잠긴 상태라서 읽을 수 없습니다. 이 잠금을 푸는 게 다음 장입니다.

    비밀번호를 Base64로 바꿔서 앱에 넣어두면 안전할까요?
    Base64는 표기만 바꾼 것입니다. 실제 앱에서도 "Base64로 바꿨으니 숨겼다"고 착각하는 실수가 자주 발견됩니다.
    4장

    AES 암호화: 같은 열쇠로 잠그고 연다

    AES는 열쇠 하나로 잠그고 같은 열쇠로 여는 암호입니다. 데이터를 16바이트 칸 단위로 처리하고, 칸이 덜 차면 채움 바이트(패딩)를 넣습니다.

    비유: 열쇠

    AES는 집 현관 열쇠와 같습니다. 잠글 때 쓴 열쇠로 그대로 엽니다. 이런 방식을 대칭키라고 합니다. 그래서 열쇠가 새면 끝입니다. Level 1은 열쇠를 앱 코드 안에 같이 넣어둔 경우입니다.

    비유: 16바이트 칸과 패딩

    AES는 16칸짜리 계란판에만 데이터를 담아서 잠글 수 있습니다. 17바이트를 담으려면 계란판이 2개 필요하고, 두 번째 판에는 15칸이 빕니다. 빈칸을 그냥 두면 잠글 수 없어서 채움 바이트(패딩)를 넣습니다. PKCS7이라는 규칙은 "채운 개수"를 숫자로 적어서 채웁니다. 15칸을 채웠으면 15를 15번 넣습니다. 열 때는 마지막 칸의 숫자를 보고 그만큼 버리면 됩니다.
    패딩이 어떻게 붙는지 보기
    원래 데이터패딩 (채운 개수를 값으로 넣음)

    글자 수를 바꿔보세요. 딱 16바이트면 어떻게 될까요? 이때는 16칸짜리 판을 하나 더 붙여서 16으로 가득 채웁니다. 그래야 열 때 "마지막 칸 = 채운 개수" 규칙이 항상 통합니다.

    16진수로 15는 0f입니다. Python 결과에서 본 \x0f가 바로 이것입니다.

    직접 해보기: 개발자가 되어 상자 만들기

    Level 1 개발자는 미리 아래 작업을 해서 결과만 앱에 넣었을 겁니다. 똑같이 해봅시다.

    문장을 AES로 잠그기
    20바이트짜리 문장을 AES로 잠그면 결과는 몇 바이트일까요?
    16칸 판 하나에 16바이트, 남은 4바이트에 판 하나가 더 필요해서 2판 = 32바이트. 두 번째 판에는 12칸이 빕니다. 그 12칸에는 0c(12)가 12번 들어갑니다.
    5장

    Java 코드를 읽기 위한 최소한의 문법

    리버싱에서 코드를 읽을 때는 문법을 다 알 필요가 없습니다. "무엇이 무엇을 부르고, 어떤 조건에서 어디로 가는지"만 따라가면 됩니다.

    보이는 모양뜻
    public class MainActivity클래스: 관련된 기능을 묶은 상자. 파일 하나에 보통 하나
    void verify(View view) { … }메서드: 이름 붙은 기능 하나. 괄호 안이 받는 값, { } 안이 하는 일
    boolean a(String str)앞의 boolean은 돌려주는 값의 종류. true/false를 돌려준다는 뜻
    return x;결과로 x를 돌려주고 메서드를 끝냄
    c.a()c 클래스의 a 메서드를 호출함 (실행시킴)
    if (조건) { … }조건이 참일 때만 안쪽을 실행함
    A || BA 또는 B 중 하나라도 참이면 참
    str.equals(x)str과 x의 내용이 같은지 비교함

    이름이 a, b, c인 이유: 난독화

    원래 개발자는 RootChecker.checkSuBinary() 같은 이름을 썼을 겁니다. 배포할 때 도구가 이름을 c.a()처럼 의미 없는 글자로 바꿔서 읽기 어렵게 만듭니다. 이걸 난독화라고 합니다. 이름은 바뀌어도 하는 일은 그대로이므로, 안을 읽어보고 우리가 이름을 다시 붙이면 됩니다. jadx에서는 이름을 클릭하고 N 키를 누르면 이름을 바꿀 수 있습니다.

    코드 따라가는 요령

    1. 시작점을 찾는다 (Manifest의 시작 화면, 버튼이 부르는 메서드)
    2. 모르는 메서드 이름이 나오면 더블클릭해서 들어간다
    3. 들어간 메서드가 무엇을 받고 무엇을 돌려주는지만 먼저 본다
    4. 알아낸 내용을 메모하거나 이름을 바꿔둔다
    5. 돌아와서 다음 줄을 읽는다
    if (c.a() || c.b() || c.c()) { a("Root detected!"); } 는 무슨 뜻일까요?
    ||는 "또는"입니다. 루팅 흔적이 하나라도 발견되면 경고를 띄웁니다. "모두"였다면 &&를 씁니다.
    6장

    비트 플래그: 숫자 하나에 스위치 여러 개

    숫자 하나를 2진수로 펼치면 0과 1로 된 스위치 줄이 됩니다. & 연산으로 그중 원하는 스위치 하나만 확인할 수 있습니다.

    비유

    벽에 스위치 8개가 한 줄로 붙어 있다고 생각해 보세요. 각 스위치는 꺼짐(0) 또는 켜짐(1)입니다. 안드로이드는 앱의 여러 설정(시스템 앱인지, 디버그 가능한지 등)을 이렇게 숫자 하나(flags)에 담아둡니다. 오른쪽에서 두 번째 스위치가 디버그 가능 스위치이고, 그 자리의 값이 2입니다.
    flags 스위치를 켜고 꺼보기

    주황 테두리가 디버그 스위치(값 2)입니다. 다른 스위치를 아무리 바꿔도 flags & 2는 디버그 스위치만 봅니다.

    Level 1 코드에서는

    public static boolean a(Context context) {
    return (context.getApplicationContext().getApplicationInfo().flags & 2) != 0;
}

    flags & 2는 "디버그 스위치만 남기고 나머지를 0으로 만든다"는 뜻입니다. 결과가 0이 아니면 디버그 스위치가 켜져 있는 것이고, 앱은 "App is debuggable!"을 띄우고 종료합니다.

    flags가 6이면 (2진수 0000 0110) 디버그 가능일까요?
    6 = 4 + 2입니다. 값 2짜리 스위치가 켜져 있으므로 6 & 2 = 2입니다. 위 스위치에서 2와 4를 켜고 확인해 보세요. 여기서 값 4짜리 스위치는 "코드가 있는 앱"이라는 뜻입니다.
    7장

    Level 1 처음부터 끝까지 다시 풀기

    이제 앞에서 배운 것으로 Level 1의 전체 흐름을 한 번에 따라갑니다. 아래 코드는 jadx가 실제로 보여주는 코드입니다.

    1단계: 시작점 찾기 (Manifest)

    <activity android:name="sg.vantagepoint.uncrackable1.MainActivity">
    <intent-filter>
        <action android:name="android.intent.action.MAIN"/>
        <category android:name="android.intent.category.LAUNCHER"/>
    </intent-filter>
</activity>

    MAIN + LAUNCHER가 붙은 화면이 앱 아이콘을 눌렀을 때 처음 뜨는 화면입니다.

    2단계: 앱이 켜질 때 하는 일 (onCreate)

    protected void onCreate(Bundle bundle) {
    if (c.a() || c.b() || c.c()) {       // 루팅 흔적 3가지 검사 (5장)
        a("Root detected!");
    }
    if (b.a(getApplicationContext())) {   // 디버그 스위치 검사 (6장)
        a("App is debuggable!");
    }
    super.onCreate(bundle);
    setContentView(R.layout.activity_main);   // 화면 배치 불러오기 = 0x7f030000
}

    5단계: 상자를 여는 곳 (sg.vantagepoint.a.a)

    public static byte[] a(byte[] bArr, byte[] bArr2) {
    SecretKeySpec secretKeySpec = new SecretKeySpec(bArr, "AES/ECB/PKCS7Padding");  // 첫 번째 인자 = 열쇠
    Cipher cipher = Cipher.getInstance("AES");
    cipher.init(2, secretKeySpec);             // 2 = DECRYPT_MODE (열기). 1이면 잠그기
    return cipher.doFinal(bArr2);              // 두 번째 인자(상자)를 열어서 돌려줌
}

    Cipher.getInstance("AES")처럼 방식을 생략하면 안드로이드는 기본값인 ECB 방식 + PKCS 패딩을 씁니다. ECB는 16바이트 칸을 하나씩 따로 잠그는 가장 단순한 방식입니다. 그래서 Python에서 modes.ECB()를 썼습니다.

    직접 해보기: 앱이 하는 일을 그대로 따라 하기

    앱 대신 상자 열기

    "열쇠 한 글자 바꿔보기"를 누르면 결과가 완전히 엉망이 됩니다. 열쇠가 조금만 달라도 전혀 열리지 않는다는 게 AES의 성질입니다. 그러니 이 앱의 문제는 AES가 약해서가 아니라 열쇠를 상자 옆에 같이 둔 것입니다.

    Python 스크립트와 비교

    key = bytes.fromhex("8d12…73cc")              # 앱의 b() 와 같음
box = base64.b64decode("5UJi…GOc=")            # 앱의 Base64.decode() 와 같음
opener = Cipher(algorithms.AES(key), modes.ECB()).decryptor()
opened = opener.update(box) + opener.finalize() # 앱의 cipher.doFinal() 과 같음
opened = opened[:-opened[-1]]                   # 앱은 Cipher가 자동으로 해주는 패딩 제거

    스크립트의 줄 하나하나가 앱 코드의 한 부분과 짝을 이룹니다. 리버싱의 마지막 단계는 이렇게 "앱이 하는 일을 내가 똑같이 재현하는 것"입니다.
